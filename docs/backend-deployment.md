# Backend deployment to AWS EC2

This repository supplies a deployment path; it has not created AWS resources or performed a live deployment. The account, region, instance, repository, database, identity provider and domain remain operator configuration. `Deploy Bugger backend to EC2` defaults to **check**, so it can validate the implementation while AWS signup is still underway.

## Deployment contract

`backend-ci.yml` runs on relevant changes and as a reusable workflow. It installs locked dependencies, runs backend unit tests, builds TypeScript, exercises PostgreSQL 16 integration tests, checks the deployment controller and Bash syntax, then builds a Linux container using the `backend/` Docker context. The image is saved as a short-lived workflow artifact. No AWS credentials are needed for these checks.

`deploy-backend.yml` runs only by manual dispatch on `main`. In **deploy** mode it consumes the verified image artifact, uses GitHub OIDC to assume an AWS role, pushes to one ECR repository, resolves its SHA-256 digest and sends an SSM command to one instance. There are no SSH keys, inbound SSH requirement or static AWS access keys in GitHub. The digest, full Git revision and region are validated before use; AWS CLI runs through `execFile` arguments. See [GitHub's AWS OIDC configuration](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws) and [ECR digest pulls](https://docs.aws.amazon.com/AmazonECR/latest/userguide/docker-pull-ecr-image.html).

The remote script runs as root under `flock` and performs these steps:

1. Verify root-owned configuration and signing key permissions; authenticate to ECR using the instance role and pull the exact digest.
2. Run the explicit `npm run migrate` command in the new image before starting it. Migrations must remain compatible with the currently deployed revision.
3. Start a candidate on **127.0.0.1:3001**, check `/readyz`, and compare `/version.revision` to the full Git commit.
4. Preserve the previous container, replace production on **127.0.0.1:3000**, then repeat readiness and revision checks. A failed replacement restarts the previous container and checks its readiness. The old container stays available until the next deployment.

Containers run as UID/GID 1000, with a read-only root filesystem, all Linux capabilities removed, no-new-privileges, a limited `/tmp`, 512 MB memory, one CPU, a PID limit and bounded Docker logs. Application secrets are read from `/etc/bugger/backend.env` and read-only mounted files; the env file is never shell-sourced. Caddy runs on the host and proxies to port 3000. Replacement has a brief interruption; this single-instance path is not a zero-downtime or highly available service.

## AWS resources to prepare

Choose one standard AWS commercial region consistently. The supplied registry/ARN validation targets the `aws` partition, not GovCloud or China.

- **EC2:** Linux x86-64 compatible with the image built on GitHub's Ubuntu runner, encrypted EBS, adequate space for current/candidate/previous images, Docker Engine, AWS CLI v2, Python 3, curl, Bash, util-linux `flock`, coreutils `timeout`, and a healthy SSM Agent. Enable Docker and SSM on boot. Use an instance role and IMDSv2. For container AWS SDK access, set the metadata response hop limit to **2**; otherwise the Docker bridge can prevent credential retrieval. [AWS container metadata guidance](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-new-instances.html).
- **Networking:** expose 80/443 to the intended users for Caddy; do not expose 22, 3000, 3001 or PostgreSQL publicly. Bind backend ports only to loopback as the script does. The instance needs outbound HTTPS to SSM, ECR, S3, Cognito/JWKS and certificate issuers via internet/NAT or appropriate endpoints. DNS must resolve. Keep RDS in private subnets and allow 5432 only from the EC2 security group.
- **ECR:** create one private repository, enable image scanning and immutable tags. The workflow uses a unique commit/run/attempt tag, then deploys only by digest. Configure lifecycle retention without removing the active and rollback images. Inspect scanning results before approving production deployment; this pipeline does not claim a vulnerability scan gate.
- **RDS PostgreSQL 16:** private endpoint, encrypted storage, backups/PITR and deletion protection appropriate to the environment. Create the `bugger` database and a dedicated database user; do not use the master user as the application login. The migration user currently needs schema DDL privileges. Download the correct AWS RDS CA bundle and install it as `/etc/bugger/database-ca.pem`. Runtime mounts it and sets `DATABASE_CA_FILE`; the backend verifies the server certificate. Avoid URL SSL parameters that override the configured CA. Rotate certificates before expiry and test restoration. [RDS PostgreSQL TLS guidance](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.SSL.html).
- **S3 for optional cloud reports:** dedicated private bucket, Block Public Access enabled, bucket-owner-enforced ownership, encryption and no public ACL/policy. The app reads/writes/deletes objects via its instance role; it needs no public bucket website or browser CORS rule. Keys currently begin with the owner hash, so the example policy scopes access to this dedicated bucket's objects. If using a customer-managed KMS key, add its narrowly scoped encrypt/decrypt permissions separately. Align versioning/retention with deletion promises; do not silently retain deleted report versions indefinitely. See backend documentation for orphan-object cleanup and retention limitations.
- **Cognito for optional cloud reports:** a user pool and public app client **without a secret**, authorization-code flow with PKCE S256, and exact approved callback/logout URLs for the final extension identity. Register the extension's actual `https://EXTENSION_ID.chromiumapp.org/` callback as implemented by its login client; match any path suffix exactly. Set the user-pool issuer (`https://cognito-idp.REGION.amazonaws.com/POOL_ID`), app client ID, reports bucket and region together. The hosted login domain is separate from the API domain. [Cognito code/PKCE endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html).

Use cloud reports only after its actual authentication client and privacy disclosure are configured and validated. An EC2 deployment does not automatically make extension cloud sync or paid checkout ready.

## IAM and GitHub setup

The JSON files in `deploy/iam/` are **templates**, not applied infrastructure. Replace every uppercase placeholder with the exact account, region, repository, instance and bucket. Never widen the OIDC subject to a repository wildcard to fix authentication.

1. Add GitHub's OIDC provider `https://token.actions.githubusercontent.com` with audience `sts.amazonaws.com`.
2. Create the GitHub deployment role using `github-oidc-trust.json` and `github-deploy-policy.json`. Set `REPLACE_WITH_EXACT_ENVIRONMENT_SUBJECT` to the repository's actual subject for **backend-production**. For legacy subjects this is `repo:OWNER/REPOSITORY:environment:backend-production`. Repositories created after July 15, 2026 (or opted into immutable claims) include IDs, for example `repo:OWNER@OWNER_ID/REPOSITORY@REPOSITORY_ID:environment:backend-production`. Use the exact owner/repository IDs and active subject format; don't invent them. The linked GitHub OIDC documentation describes both formats.
3. Create an EC2 role/instance profile with `ec2-role-trust.json`, `ec2-app-policy.json`, and the AWS-managed `AmazonSSMManagedInstanceCore` policy. The GitHub role needs no database password, signing key, S3 object access or `iam:PassRole`. Its SSM SendCommand permission grants root execution on the one named instance; protect the workflow and environment accordingly. Registry authentication and command-invocation polling use `Resource: "*"` because those API operations do not support the same per-resource restriction as ECR repository or SendCommand operations.
4. In GitHub create **backend-production**, restrict deployment branches to **main**, and configure required reviewers if your plan supports them. Protect `main` and deployment workflow changes. Environment restrictions are an operator setup step; YAML cannot create those settings.
5. Add environment **variables**: `AWS_REGION`, `AWS_ACCOUNT_ID`, `AWS_DEPLOY_ROLE_ARN`, `ECR_REPOSITORY` (repository name, not full URI), and `EC2_INSTANCE_ID`. No static AWS secrets are required. Runtime secrets belong on EC2 or an approved secret manager, not in these variables or artifacts.

## Runtime files and keys

Using an authenticated SSM administrative session, create `/etc/bugger` owned by root and group 1000, mode 750. Install a completed copy of `deploy/backend.env.example` at `/etc/bugger/backend.env`, root:root **600**. Docker reads this file as root; the app process remains non-root. Values are Docker env-file syntax, not shell commands. URL-encode reserved characters in the database password. Keep real values out of git and shell history.

Generate an ES256 P-256 private key securely (for example `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out signing-private.pem`), and install it at `/etc/bugger/signing-private.pem`, root:1000 **640**. Keep the key stable between deployments; the container sees `/run/secrets/signing-private.pem`. Publish/configure only its public counterpart for extension verification. `SIGNING_KEY_ID`, issuer, audience and the extension's trust configuration must agree. Generate a separate high-entropy license-key pepper of at least 32 bytes and preserve it; changing it invalidates stored license-key lookup hashes. Back up both secrets securely, with a documented rotation procedure.

Install the RDS CA file root-owned and readable by UID 1000. Set `JWT_ISSUER` to the final HTTPS API origin. `HOST`, `PORT`, signing path and Git revision are enforced by the deployment script. `TRUST_PROXY=false` is conservative in the supplied topology: the Docker bridge means Caddy's connection is not loopback inside the container. Requests therefore share the gateway IP for IP-based rate limits until an operator configures the exact trusted peer. The backend accepts one explicit IPv4/IPv6 address: inspect `docker network inspect bridge --format '{{(index .IPAM.Config 0).Gateway}}'` and confirm that address is the actual Caddy-to-container peer in your topology, then set `TRUST_PROXY` to that one address. Keep published ports loopback-only and Caddy's default forwarded-header replacement; do not trust arbitrary client forwarding headers, all proxies, hop counts or broad CIDRs. Recheck the value after Docker network changes.

## Domain and HTTPS

The API domain is configurable and need not be selected to run check mode. Once chosen, point its DNS A record (and only a working IPv6 AAAA record, if applicable) to the server. Install Caddy as a host service. Copy `deploy/Caddyfile` to `/etc/caddy/Caddyfile` and configure the service environment using `deploy/caddy-environment.conf.example` as a systemd override with your real `BUGGER_API_DOMAIN` and `ACME_EMAIL`. Reload systemd, validate the Caddy configuration under the same environment, then restart/reload Caddy.

Caddy's [environment placeholders](https://caddyserver.com/docs/caddyfile/concepts) keep the domain out of source. Ensure ports 80/443 and outbound certificate traffic are available. Until DNS and valid TLS work, use SSM-local readiness checks; do not point the extension at plaintext HTTP production endpoints. After a deployment verify HTTPS `/readyz` and `/version` externally as well as the local checks. The workflow's successful SSM result confirms local readiness, not public DNS/TLS reachability.

## Operating the pipeline

Choose **Actions → Deploy Bugger backend to EC2 → Run workflow → main → check** first. All checks run without AWS. After setup and review, choose **deploy**. The protected job pushes the artifact and sends one SSM command. No deployment runs automatically on push.

SSM polling accepts only explicit success with response code zero. Pending/delayed processing is bounded to 180 five-second polling iterations; each CLI request has a 30-second deadline, remote execution 900 seconds, and the deployment job 30 minutes. The controller handles eventual command discovery and suppresses remote stdout/stderr because application errors can contain private data. It does not repeat a mutating SendCommand after network errors. [SSM invocation states](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_GetCommandInvocation.html).

If the runner times out, the command might still be executing. Inspect SSM and the instance before retrying. Use authorized SSM sessions to inspect `docker ps`, container health and bounded logs without copying secrets into tickets. A failed candidate leaves the current container serving. A failed production replacement attempts to restart the preserved previous container; check its health immediately if an error is reported. Host failure, Docker failure or forced process termination can still require operator recovery. Database migrations are not rolled back: destructive migrations require a separate backup and staged migration plan. Verify backups and rollback behavior in staging before first production use.

## What was verified

Three sandboxed shell tests execute the rollout state machine with mock Docker/AWS/curl commands: successful replacement, candidate failure preserving production, and production failure restoring the previous container. Local mocked controller tests cover immutable image/instance/region validation, shell injection rejection, exact SSM argument construction, eventual consistency, success/response-code handling, failures, unknown states, bounded polling, sanitized errors and Bash syntax. TypeScript and workflow YAML parsing are checked locally. The workflows define real PostgreSQL integration and Docker builds, but no AWS account resources, live OIDC role assumption, ECR push, SSM execution, TLS certificate or production rollback has been executed in this setup session. Those require the account and configured resources above.
